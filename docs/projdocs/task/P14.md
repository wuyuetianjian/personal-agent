How to use:

- Configure the Leader model under `agent.leader.model_id`.
- Keep `agent.planner.enabled: true` and set `agent.planner.max_nodes` in the mountable config file.
- Ensure the selected model has `chat` and `json_schema` capabilities in `models.registry`.
- Configure optional `agent.subagents.reasoning` and `agent.subagents.synthesis` settings to tune local model temperature and output token limits.
- Enable `rag.vector` with `embedding_model_id`, Qdrant base URL, collection, and optional API key env to use hybrid retrieval.
- Enable `rag.reranker` with a rerank-capable model id when a compatible provider is available.
- Enable `browser.enabled` and configure allowed domains under `browser.profile_reuse.allowed_domains` for governed browser navigation/write execution.
- Enable coding backends under `coding_agents.backends` and use `coding.<backend>` workflow nodes with structured JSON input.
- Configure MCP servers under `mcp.servers` and list exposed tools with `tools` to use `mcp.<server>.<tool>` workflow nodes.
- Use `pachat mcp list/health/tools/test --config <path>` to inspect configured MCP servers and smoke-test a configured tool through Runtime workflow execution.
- Configure fixed local command actions under `tools.allowlist` to use `tool.<id>` workflow nodes.
- Open `GET /dashboard` from `pachat serve` to use the minimal operator console for run/task/workflow/approval/notification/project/skill/capability views.
- Subscribe to `GET /dashboard/events` for typed dashboard SSE; pass `Last-Event-ID` on reconnect to skip older snapshots.
- Use `GET /evidence?task_id=<task_id>` or the dashboard Evidence view to inspect claims, evidence previews, source/trust/privacy metadata, and verification status.
- Use `pachat backup restore --config <path> --input <backup.zip> --dry-run=false --force` to perform a validated restore over an existing stopped database.
- Use `pachat export --config <path> --output portable.json` to write a portable JSON artifact, and `pachat import --config <path> --input portable.json` to restore it into another local database.
- Use `pachat run --config <path> --task "<task>" --stream` to emit planning, workflow, node/tool, approval wait, and answer stream progress for a foreground task.
- Use REST list endpoints with `limit`, `offset`, and supported filters, including `/tasks`, `/workflows`, `/events`, `/notifications`, `/projects`, `/triggers`, and `/skills`.
- Run `go test ./internal/e2e -run FunctionalRC` to execute the Functional RC gate for local memory/RAG, model planning, Browser, Codex-style coding, Claude-style review, MCP, public escalation, idempotency/restart, and watcher notification scenarios.
- Run `pachat release check --quick` to execute the normal quick release checks plus mandatory Functional GA gates for planning, external executor wiring, restart recovery, privacy escalation, early-stop cancellation, idempotency, notification semantics, and Functional RC E2E coverage.
- Run `pachat release soak --config <path> --duration <duration> --interval <interval> --output <report.json>` to execute the soak gate. Keep the default `--offline=true` for local mandatory validation, or set `--offline=false` in release-candidate environments with configured external model/browser/CLI backends.
- Run `pachat release recovery-drill --config <path> --work-dir <dir> --output <report.json>` to execute the data-loss recovery drill against disposable fixture state without deleting the user's configured database.
- Run `pachat release perf-baseline --config <path> --work-dir <dir> --output <report.json>` to record startup, local query, hybrid RAG fallback, workflow dispatch, memory, and concurrent workflow metrics from an isolated Runtime fixture.
- Enable a `public_remote` chat model and configure `privacy.hmac_secret_env` to allow governed public escalation when local evidence is insufficient.
- Register active read-only Skills with workflow nodes to let high-confidence matches bypass Leader planning and execute directly through persisted workflows.
- Run `pachat serve --config <path>` to start the background workflow worker; startup recovery resumes `pending`, `running`, and `retrying` workflows.
- Use configured non-read-only workflow capabilities normally; Runtime claims the workflow node `idempotency_key` before side effects execute.
- Pass `--project <project_id>` for CLI task runs or `project_id` for API task creation to enforce project Skill, model, capability, public escalation, and coding backend allowlists.
- Enable `coding_agents.cross_review.enabled` and configure `large_diff_bytes` to require a second backend only for triggered coding review policy cases.
- Run `PACHAT_CODING_AGENT_E2E=1` with `PACHAT_CODEX_CLI_PATH` or `PACHAT_CLAUDE_CODE_CLI_PATH` to execute real coding CLI E2E tests.
- Use condition-watch triggers normally; daemon ticks persist state transition and notification timestamps.
- Configure `proactive.enabled` and `proactive.poll_interval`, then run `pachat serve --config <path>` to recover triggers/watchers and continuously dispatch due trigger work into Runtime workflows.
- Use `pachat skill validate/import/list/show/versions/enable/disable/run --config <path>` to operate persisted Skill manifests and run enabled Skills through Runtime workflows.
- Use notification store policy writes to deduplicate notifications, record severity/delivery state, and defer during quiet hours.
- Use `goal.Store` to persist bounded goals and milestones and re-evaluate them through the bounded planner.
- Query usage with `pachat task usage --config <path> --id <task_id>`.

Runtime data locations:

- Planner state is not persisted separately.
- Planned nodes are persisted through the existing workflow tables and checkpoints.
- Model reasoning summaries are stored as model evidence.
- Model synthesis answers are stored in workflow checkpoints and persisted to the task final answer.
- Vector index data lives in the configured Qdrant collection; local document/chunk metadata remains in SQLite.
- Browser read observations are stored in the existing `evidence` table with source type `browser`.
- Coding execution summaries, files changed, diffs, and test command evidence are stored in the existing `evidence` table with source type `tool`.
- MCP outputs are stored in the existing `evidence` table as `UNTRUSTED OBSERVATION` source type `tool`.
- Allowlisted local tool command/output records are stored in the existing `evidence` table with source type `tool`.
- Public escalation does not create local evidence; provider usage is propagated into task usage when escalation is invoked.
- Usage is read from workflow checkpoints and aggregated in memory for query/reporting.
- Early stop decisions use persisted evidence and completed node claims; cancelled pending nodes do not add usage checkpoints.
- Cancellation uses caller contexts across Runtime workflow execution, model HTTP requests, vector HTTP requests, governed browser/MCP/tool executors, MCP/tool child processes, and coding process runners.
- Skill-driven workflows are persisted in the existing workflow tables with the matched Skill ID and version.
- Background worker state is the existing `workflow_runs`, `workflow_nodes`, and `workflow_checkpoints` tables; no separate queue table is required.
- Side-effect idempotency state is stored in the `side_effect_records` table keyed by workflow node idempotency key.
- Project allowed model state is stored in the `projects.allowed_models_json` column.
- Coding Cross Review uses the existing coding backend registry and stores review command/test evidence in the coding execution evidence record.
- Real coding CLI E2E tests use temporary git repositories and leave default test runs skipped unless explicitly enabled.
- Condition watcher state is stored in the existing `trigger_state` table.
- Notification policy state is stored in the existing `notification_inbox` table.
- Goal runtime state is stored in `goals` and `goal_milestones`.
- Proactive daemon runtime state uses the existing trigger state/history tables and creates pending workflow rows for the background workflow worker.
- Skill operator state is stored in the existing `skills` and `skill_versions` tables.
- MCP CLI state is read from mountable config; `mcp test` writes task/workflow/evidence rows through the existing Runtime path.
- Dashboard data is read from existing local APIs, Runtime capability registry, and SQLite task/workflow/project/skill/trigger/notification/approval stores.
- Dashboard SSE cursors are stable timestamp-prefixed event IDs derived from local task/workflow/approval/notification/trigger timestamps.
- Evidence viewer data is read from `evidence`, `claims`, and `claim_evidence`; sensitive or confidential content is redacted in the default preview.
- Full restore writes a timestamped `<database>.pre-restore-*` copy before replacement and validates the restored SQLite database before reporting success.
- Portable export/import data is stored in user-selected JSON artifact files. The artifact includes project rows, skill rows and versions, selected episodic/semantic memory, and `documents` metadata only; it excludes config secrets, credentials, browser cookie/password/profile data, coding CLI credential stores, and `document_chunks.text`.
- Streaming CLI progress is emitted directly to stdout for foreground runs and is not persisted as a separate stream. Durable state remains in task, workflow, checkpoint, evidence, and approval tables.
- REST pagination/filtering reads from existing SQLite task, workflow, event, notification, project, trigger, and skill tables; responses include `pagination` metadata and do not create new persistence tables.
- Functional RC E2E data uses temporary SQLite databases, temporary repositories, mock-backed external executors, local httptest public-provider endpoints, and the normal workflow/evidence/side-effect/trigger/notification tables.
- Soak report data is emitted to stdout and optionally written to a user-selected JSON path; workload state is stored in the configured SQLite database using normal task, workflow, checkpoint, evidence, and notification tables.
- Recovery drill report data is emitted to stdout and optionally written to a user-selected JSON path; fixture backup/restore state lives under the selected work directory and uses isolated SQLite databases.
- Performance baseline report data is emitted to stdout and optionally written to a user-selected JSON path; fixture state lives in an isolated SQLite database under the selected work directory.
