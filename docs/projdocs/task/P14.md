How to use:

- Configure the Leader model under `agent.leader.model_id`.
- Keep `agent.planner.enabled: true` and set `agent.planner.max_nodes` in the mountable config file.
- Ensure the selected model has `chat` and `json_schema` capabilities in `models.registry`.
- Configure optional `agent.subagents.reasoning` and `agent.subagents.synthesis` settings to tune local model temperature and output token limits.
- Enable `rag.vector` with `embedding_model_id`, Qdrant base URL, collection, and optional API key env to use hybrid retrieval.
- Enable `rag.reranker` with a rerank-capable model id when a compatible provider is available.
- Enable `browser.enabled` and configure allowed domains under `browser.profile_reuse.allowed_domains` for governed browser navigation/write execution.
- Enable coding backends under `coding_agents.backends` and use `coding.<backend>` workflow nodes with structured JSON input.
- Configure MCP servers under `mcp.servers` and list exposed tools with `tools` to use `mcp.<server>.<tool>` workflow nodes.
- Configure fixed local command actions under `tools.allowlist` to use `tool.<id>` workflow nodes.
- Enable a `public_remote` chat model and configure `privacy.hmac_secret_env` to allow governed public escalation when local evidence is insufficient.
- Register active read-only Skills with workflow nodes to let high-confidence matches bypass Leader planning and execute directly through persisted workflows.
- Run `pachat serve --config <path>` to start the background workflow worker; startup recovery resumes `pending`, `running`, and `retrying` workflows.
- Use configured non-read-only workflow capabilities normally; Runtime claims the workflow node `idempotency_key` before side effects execute.
- Pass `--project <project_id>` for CLI task runs or `project_id` for API task creation to enforce project Skill, model, capability, public escalation, and coding backend allowlists.
- Enable `coding_agents.cross_review.enabled` and configure `large_diff_bytes` to require a second backend only for triggered coding review policy cases.
- Run `PACHAT_CODING_AGENT_E2E=1` with `PACHAT_CODEX_CLI_PATH` or `PACHAT_CLAUDE_CODE_CLI_PATH` to execute real coding CLI E2E tests.
- Use condition-watch triggers normally; daemon ticks persist state transition and notification timestamps.
- Use notification store policy writes to deduplicate notifications, record severity/delivery state, and defer during quiet hours.
- Use `goal.Store` to persist bounded goals and milestones and re-evaluate them through the bounded planner.
- Query usage with `pachat task usage --config <path> --id <task_id>`.

Runtime data locations:

- Planner state is not persisted separately.
- Planned nodes are persisted through the existing workflow tables and checkpoints.
- Model reasoning summaries are stored as model evidence.
- Model synthesis answers are stored in workflow checkpoints and persisted to the task final answer.
- Vector index data lives in the configured Qdrant collection; local document/chunk metadata remains in SQLite.
- Browser read observations are stored in the existing `evidence` table with source type `browser`.
- Coding execution summaries, files changed, diffs, and test command evidence are stored in the existing `evidence` table with source type `tool`.
- MCP outputs are stored in the existing `evidence` table as `UNTRUSTED OBSERVATION` source type `tool`.
- Allowlisted local tool command/output records are stored in the existing `evidence` table with source type `tool`.
- Public escalation does not create local evidence; provider usage is propagated into task usage when escalation is invoked.
- Usage is read from workflow checkpoints and aggregated in memory for query/reporting.
- Early stop decisions use persisted evidence and completed node claims; cancelled pending nodes do not add usage checkpoints.
- Cancellation uses caller contexts across Runtime workflow execution, model HTTP requests, vector HTTP requests, governed browser/MCP/tool executors, MCP/tool child processes, and coding process runners.
- Skill-driven workflows are persisted in the existing workflow tables with the matched Skill ID and version.
- Background worker state is the existing `workflow_runs`, `workflow_nodes`, and `workflow_checkpoints` tables; no separate queue table is required.
- Side-effect idempotency state is stored in the `side_effect_records` table keyed by workflow node idempotency key.
- Project allowed model state is stored in the `projects.allowed_models_json` column.
- Coding Cross Review uses the existing coding backend registry and stores review command/test evidence in the coding execution evidence record.
- Real coding CLI E2E tests use temporary git repositories and leave default test runs skipped unless explicitly enabled.
- Condition watcher state is stored in the existing `trigger_state` table.
- Notification policy state is stored in the existing `notification_inbox` table.
- Goal runtime state is stored in `goals` and `goal_milestones`.
